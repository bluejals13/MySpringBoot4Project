 # PRD — Lab 2-5 Publisher–Book 관계 확장

 ## 1\. 프로젝트 목적

 기존 `Book–BookDetail` 도서 관리 시스템에 `Publisher`를 추가하고, `Publisher`와 `Book` 간 **1:N 연관관계**를 구현한다.

 기존:

```
Book 1 ─── 1 BookDetail
```

 변경:

```
Publisher 1 ─── N Book 1 ─── 1 BookDetail
```

 - 하나의 `Publisher`는 여러 `Book`을 가질 수 있다.
- 하나의 `Book`은 하나의 `Publisher`에 소속된다.
- 기존 `Book ↔ BookDetail` 1:1 관계는 유지한다.
- `BookDetail` 전용 Controller/Service는 사용하지 않고 Book 기능에 포함하여 관리한다.

 ## 2\. Publisher 기능

 `Publisher`에 대한 다음 기능을 제공한다.

 - Publisher 전체 조회
- Publisher 단건 조회
- Publisher 이름으로 조회
- Publisher 생성
- Publisher 수정
- Publisher 삭제
- 특정 Publisher의 Book 목록 조회

 추가로:

 - Publisher 이름 중복을 검증한다.
- 도서가 존재하는 Publisher는 삭제할 수 없다.
- Publisher 조회 시 보유 Book 수를 확인할 수 있어야 한다.

 ## 3\. Book 기능

 기존 Book 기능을 유지하면서 Publisher 연관 기능을 추가한다.

 - Book 전체 조회
- Book 단건 조회
- ISBN으로 조회
- 저자로 검색
- 제목으로 검색
- Publisher별 조회
- Book 생성
- Book 수정
- Book 삭제

 Book 생성 및 수정 시:

 - Publisher를 지정할 수 있어야 한다.
- 존재하지 않는 Publisher를 지정할 수 없다.
- ISBN 중복을 검증한다.

 Book 조회 시 필요한 경우 다음 정보를 함께 조회한다.

```
Book
├── Publisher
└── BookDetail
```

 ## 4\. BookDetail 기능

 기존 `Book ↔ BookDetail` 기능을 유지한다.

 - Book과 BookDetail의 1:1 관계를 유지한다.
- Book 조회 시 BookDetail을 함께 조회할 수 있어야 한다.
- Book 삭제 시 기존 관계에 따라 BookDetail도 함께 처리한다.
- 별도의 `BookDetailController`, `BookDetailService`는 사용하지 않는다.

 ## 5\. DTO 구성

 DTO는 다음 **3개만 사용한다.**

```
dto
├── BookDTO.java
├── BookDetailDTO.java
└── PublisherDTO.java
```

 ### BookDTO

```
BookDTO
├── Request
├── Response
├── SimpleResponse
└── BookDetailResponse
```

 `Request`에는 Publisher 지정에 필요한 `publisherId`와 BookDetail 정보를 포함한다.

 ### PublisherDTO

```
PublisherDTO
├── Request
├── Response
└── SimpleResponse
```

 Publisher Response에는 필요한 경우 Book 목록과 Book 수를 포함한다.

 ### BookDetailDTO

 BookDetail의 상세 정보를 표현한다.

```
BookDetailDTO
├── description
├── language
├── pageCount
├── publisher
├── coverImageUrl
└── edition
```

 ## 6\. 계층 구조

 핵심적인 책임 구조는 다음과 같다.

```
BookController
      │
      ▼
BookService
   ├── Book
   ├── BookDetail
   └── Publisher
```

 Publisher는 독립적으로 관리한다.

```
PublisherController
      │
      ▼
PublisherService
      │
      └── Publisher
```

 따라서 다음 구조는 사용하지 않는다.

```
BookDetailController
BookDetailService
```

 ## 7\. Repository 요구사항

 ### BookRepository

 다음 기능을 제공한다.

 - ISBN 조회
- 저자 검색
- 제목 검색
- BookDetail Fetch Join
- ISBN + BookDetail Fetch Join
- Book + BookDetail + Publisher Fetch Join
- Publisher별 Book 조회
- Publisher별 Book 수 조회
- ISBN 존재 여부 확인

 ### PublisherRepository

 다음 기능을 제공한다.

 - 이름으로 Publisher 조회
- Publisher와 Book을 함께 조회
- 이름 중복 여부 확인

 ## 8\. 초기 데이터

 `BookDataInitRunner`를 통해 Publisher와 Book 및 BookDetail의 관계가 확인 가능한 샘플 데이터를 생성한다.

 초기 데이터는 다음 관계를 확인할 수 있어야 한다.

```
Publisher
 ├── Book
 ├── Book
 └── Book
```

 그리고 각 Book은 필요에 따라:

```
Book
 └── BookDetail
```

 을 가진다.

 ## 9\. API 요구사항

 Publisher API:

```
GET    /api/publishers
GET    /api/publishers/{id}
GET    /api/publishers/name/{name}
GET    /api/publishers/{id}/books
POST   /api/publishers
PUT    /api/publishers/{id}
DELETE /api/publishers/{id}
```

 Book API는 기존 CRUD 및 조회 기능을 유지하면서 Publisher 연관 기능을 포함한다.

 ## 10\. 테스트 및 완료 기준

 다음 사항이 정상적으로 동작하는 것을 목표로 한다.

 - Publisher CRUD가 정상 동작한다.
- Publisher ↔ Book `1:N` 관계가 정상 동작한다.
- Publisher별 Book 조회가 가능하다.
- Book에서 Publisher 정보를 조회할 수 있다.
- Book의 기존 조회/검색/CRUD 기능이 유지된다.
- Book ↔ BookDetail `1:1` 관계가 유지된다.
- Publisher 이름 중복 검증이 동작한다.
- Book ISBN 중복 검증이 동작한다.
- 도서가 존재하는 Publisher의 삭제가 제한된다.
- Repository의 Fetch Join 및 조회 기능이 정상 동작한다.
- 전체 테스트가 오류 없이 통과한다.
