# Repository 테스트 수정 및 핵심 가치 정리

 ## 1\. 테스트가 수정된 가장 큰 이유

 이번 테스트 수정의 **가장 큰 원인은 `setUp()`의 데이터 준비 방식과 현재 Spring Boot/JPA 테스트 실행 환경의 불일치**였습니다.

 | 원인 | 문제 |
| --- | --- |
| `setUp()`에서 `EntityManager.persist()` 직접 사용 | JPA `persist()`는 트랜잭션이 필요함 |
| 기존 `@BeforeEach` 실행 구조 | `setUp()`에서 실제 트랜잭션이 보장되지 않아 `TransactionRequiredException` 발생 |
| Spring Boot 4 + Hibernate 7 환경 | 기존 테스트 코드가 현재 JPA 실행 방식과 완전히 일치하지 않는 부분 발생 |
| `flush()` / `clear()` 사용 | 영속성 컨텍스트와 DB 상태를 분리해서 검증하려는 테스트이므로 적절한 트랜잭션 환경 필요 |
| Book ↔ BookDetail ↔ Publisher 관계 | 테스트 데이터 생성 순서와 연관관계 설정이 현재 Entity 구조와 맞아야 함 |

실제로 첫 실행에서는 Repository 메서드의 문제가 아니라:

```
BookRepositoryTest.setUp()
PublisherRepositoryTest.setUp()
        ↓
entityManager.persist()
        ↓
TransactionRequiredException
```

 으로 테스트가 시작되기도 전에 실패했습니다.

 따라서 핵심 수정은 **Repository 테스트의 목적을 바꾸는 것이 아니라 `setUp()`이 정상적으로 테스트 데이터를 준비할 수 있도록 실행 환경과 Entity 구조를 맞추는 것**이었습니다.

 # 2\. 수정과 변경이 있었음에도 보존된 핵심 가치

 이번 수정에서 가장 중요한 원칙은:

 > **테스트의 구현 방식은 수정할 수 있지만, 테스트가 검증하는 Repository의 계약과 목적은 유지한다.**

 입니다.

 | 테스트 영역 | 수정될 수 있었던 부분 | 끝까지 보존된 핵심 가치 |
| --- | --- | --- |
| 테스트 데이터 생성 | `setUp()` 및 트랜잭션 처리 | 실제 Book/Publisher 데이터를 기반으로 Repository 검증 |
| JPA 환경 | Spring Boot 4 / Hibernate 7에 맞게 조정 | 실제 JPA Repository 동작 검증 |
| Book-Detail 관계 | Entity 관계에 맞게 데이터 구성 | Book과 BookDetail 연관관계 검증 |
| Book-Publisher 관계 | Publisher 선 저장 후 Book 연결 | Book과 Publisher 관계 검증 |
| `flush()` / `clear()` | 실행 환경에 맞게 사용 | 영속성 컨텍스트가 아닌 DB 조회 결과 검증 |
| 조회 테스트 | Repository 구현에 맞게 조정 | 실제 조회 결과와 DTO가 아닌 Entity 상태 검증 |
| assertion | 필요한 범위에서 유지 | 조회 결과의 존재 여부와 주요 값 검증 |

즉, **테스트 코드의 모양은 변경될 수 있었지만 검증하려는 계약은 변경하지 않은 것**입니다.

 # 3\. 각 테스트가 실제로 증명하는 것

 ## BookRepositoryTest

 | 테스트 | 증명하는 것 |
| --- | --- |
| `findByIsbn_ShouldReturnBook` | ISBN으로 정확한 Book을 조회할 수 있음 |
| `findByIsbn_ShouldReturnEmpty_WhenNotFound` | 존재하지 않는 ISBN에 대해 빈 결과를 반환함 |
| `findByIdWithAllDetails_ShouldReturnBookWithAllDetails` | Book 조회 시 BookDetail과 Publisher를 함께 가져올 수 있음 |
| `findByPublisherId_ShouldReturnBooks` | 특정 Publisher의 Book 목록을 조회할 수 있음 |
| `countByPublisherId_ShouldReturnCorrectCount` | 특정 Publisher가 가진 Book 수를 정확하게 계산함 |
| `existsByIsbn_ShouldReturnTrue` | 존재하는 ISBN을 정확히 판별함 |
| `existsByIsbn_ShouldReturnFalse` | 존재하지 않는 ISBN을 정확히 판별함 |
| `findByAuthorContainingIgnoreCase_ShouldReturnBooks` | Author 부분 검색 \+ 대소문자 무시가 정상 동작함 |
| `findByTitleContainingIgnoreCase_ShouldReturnBooks` | Title 부분 검색 \+ 대소문자 무시가 정상 동작함 |

### BookRepository의 핵심 증명

```
BookRepository
      │
      ├── 단건 조회
      ├── 존재 여부
      ├── 조건 검색
      ├── 관계 조회
      └── 집계
```

 즉 **Book Repository가 단순 CRUD뿐 아니라 실제 서비스에서 필요한 조회 계약을 제대로 수행하는지 증명**합니다.

| --- | --- |
| `findByName_ShouldReturnPublisher` | Publisher 이름으로 정확한 Publisher를 조회함 |

### PublisherRepository의 핵심 증명

```
PublisherRepository
      │
      ├── 단건 조회
      ├── 존재 여부
      └── Publisher → Books 관계 조회
```

 즉 **Publisher 자체의 조회 기능과 Publisher-Book 관계 조회가 정상적으로 동작하는지를 증명**합니다.

 # 5\. 전체 테스트의 검증 매트릭스

 | 기능 | BookRepository | PublisherRepository | 핵심 검증 |
| --- | --- | --- | --- |
| 단건 조회 | ✓ | ✓ | Repository 조회 계약 |
| 존재 여부 | ✓ | ✓ | `existsBy...` 계약 |
| 존재하지 않는 데이터 | ✓ | ✓ | `Optional.empty()` 처리 |
| 부분 문자열 검색 | ✓ | - | 검색 조건 |
| 대소문자 무시 검색 | ✓ | - | `IgnoreCase` |
| Publisher → Book | ✓ | ✓ | 양방향 관계 조회 |
| Book → Publisher | ✓ | - | Book의 Publisher 관계 |
| Book → BookDetail | ✓ | - | 1:1 관계 조회 |
| Count | ✓ | - | Publisher별 Book 수 |
| Fetch Join/연관 조회 | ✓ | ✓ | 연관 Entity 조회 |
| 실제 DB 반영 | ✓ | ✓ | JPA/Hibernate 동작 |
| 영속성 컨텍스트 분리 | ✓ | ✓ | `flush/clear` 이후 조회 |

 # 6\. 최종적으로 이 테스트들이 증명하는 것

 가장 중요하게 보면 이 테스트들은 단순히

 > "`findByIsbn()`이 호출되는가?"

 를 확인하는 테스트가 아닙니다.

 전체적으로 다음 구조를 증명합니다.

```
                 Repository Layer
                       │
          ┌────────────┴────────────┐
          │                         │
    BookRepository          PublisherRepository
          │                         │
     ┌────┼────┐              ┌─────┼─────┐
     │    │    │              │     │     │
   조회  검색  관계           조회  존재  관계
     │    │    │              │     │     │
     └────┴────┴──────────────┴─────┴─────┘
                       │
                       ▼
                실제 JPA / DB
                       │
              ┌────────┼────────┐
              ▼        ▼        ▼
            Book   BookDetail Publisher
```

 따라서 최종적인 테스트의 핵심 가치는:

 > **현재 Entity 관계와 JPA Repository 구현이 실제 DB 환경에서 의도한 조회·검색·존재 확인·집계·연관관계 조회를 정상적으로 수행한다는 것을 증명하는 것**입니다.

 그리고 이번 수정에서 **바뀐 것은 이 증명을 수행하기 위한 테스트 환경과 `setUp()`의 안정성이지, 이 증명이 요구하는 핵심 계약 자체가 아닙니다.**

 현재 마지막 실행 결과도 이를 뒷받침합니다.

```
Tests run: 15
Failures: 0
Errors: 0
Skipped: 0

BUILD SUCCESS
```

 즉 **Book 9개 + Publisher 5개 + Application context 1개 = 총 15개 테스트가 모두 통과**했고, Repository 테스트의 본래 검증 가치가 유지된 상태입니다.
