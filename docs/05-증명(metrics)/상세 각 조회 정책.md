# Book API 검증 결과 정리

 ## 1\. BookDetail 조회 검증

 `Book → BookDetail` 관계에서 **BookDetail이 있는 경우와 없는 경우를 모두 검증**했다.

 ### BookDetail이 없는 Book

```
curl -s http://localhost:8080/api/books/isbn/978-0134685991
```

 결과:

```
{
  "id": 5,
  "title": "Another Java Book",
  "author": "Test Author",
  "isbn": "978-0134685991",
  "price": 30000,
  "publishDate": "2023-01-01",
  "publisher": {
    "id": 2,
    "name": "O'Reilly Media",
    "establishedDate": "2022-01-01",
    "address": "New Address",
    "bookCount": null
  },
  "detail": null
}
```

 → **BookDetail이 없어도 Book 자체는 정상 조회됨.**

 ### BookDetail이 있는 Book

```
curl -s http://localhost:8080/api/books/isbn/978-1617292545
```

 결과:

```
{
  "id": 6,
  "title": "Spring Boot in Action",
  "author": "Craig Walls",
  "isbn": "978-1617292545",
  "price": 45000,
  "publishDate": "2016-01-30",
  "publisher": {
    "id": 3,
    "name": "Manning Publications",
    "establishedDate": "1997-01-01",
    "address": "20 Baldwin Road, Shelter Island, NY",
    "bookCount": null
  },
  "detail": {
    "id": 2,
    "description": "A developers guide to Spring Boot",
    "language": "English",
    "pageCount": 264,
    "publisher": "Manning Publications",
    "coverImageUrl": "https://example.com/spring-boot-in-action.jpg",
    "edition": "1st Edition"
  }
}
```

 → **BookDetail이 존재하는 경우 Book과 Detail이 정상적으로 함께 조회됨.**

 따라서 조회 쿼리가 다음과 같은 형태라면 의도에 맞게 동작한다.

```
@Query("""
    SELECT b
    FROM Book b
    LEFT JOIN FETCH b.bookDetail
    WHERE b.isbn = :isbn
    """)
Optional<Book> findByIsbnWithBookDetail(
        @Param("isbn") String isbn
);
```

 ### `LEFT JOIN FETCH`의 의미

```
Book
 ├─ BookDetail 없음
 │    └─ Book 조회 O / detail = null
 │
 └─ BookDetail 있음
      └─ Book 조회 O / detail 객체 반환
```

 반면 `JOIN FETCH`는 사실상 `INNER JOIN`이므로 BookDetail이 없는 Book은 조회 결과에서 제외될 수 있다.

 따라서 **BookDetail이 선택적 관계라면 `LEFT JOIN FETCH`가 적절하다.**

 # 2\. DELETE 검증

 Book ID=6 삭제:

```
curl -s -X DELETE http://localhost:8080/api/books/6
echo
```

 이후 조회:

```
curl -s -i http://localhost:8080/api/books/6
echo
```

 결과:

```
HTTP/1.1 404
```

```
{
  "status": 404,
  "message": "Book not found with id: 6"
}
```

 ### 검증 결과

 | 항목 | 결과 |
| --- | --- |
| DELETE 요청 | 성공 |
| 삭제 후 재조회 | 404 |
| 존재하지 않는 Book 처리 | 정상 |
| 예외 메시지 | 정상 |

즉, **삭제 후 해당 리소스가 실제로 더 이상 조회되지 않는 것까지 확인됨.**

 # 3\. PUT 수정 검증

 삭제된 ID=6에 대해 수정 요청:

```
curl -s -X PUT http://localhost:8080/api/books/6 \
  -H "Content-Type: application/json" \
  -d '{
    "title": "Spring Boot in Action 수정본",
    "author": "Craig Walls",
    "isbn": "978-1617292545",
    "price": 50000,
    "publishDate": "2016-01-30",
    "publisherId": 3
  }'
echo
```

 결과:

```
{
  "status": 404,
  "message": "Book not found with id: 6"
}
```

 ### 검증 결과

 삭제된 Book에 대해 PUT을 요청했을 때:

```
Book ID 6 존재
      ↓
DELETE
      ↓
Book ID 6 삭제
      ↓
PUT /books/6
      ↓
404 Book not found
```

 정상적인 동작이다.

 즉, **존재하지 않는 리소스를 수정하려는 요청을 허용하지 않는다.**

## 결론

 현재 구현은 **기능 검증 단계에서는 안정적인 상태**라고 판정한다

 특히 단순히 정상 케이스만 테스트한 것이 아니라,

```
정상 조회
정상 생성
정상 수정
정상 삭제
        +
중복 데이터
존재하지 않는 데이터
Validation 오류
BookDetail 존재
BookDetail 미존재
삭제 후 재조회
삭제 후 수정
```
CRUD + 예외 처리 + 연관관계 조회에 대한 기본적인 검증함
